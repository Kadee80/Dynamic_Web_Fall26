The Button Component

One reusable component, and the problems that come with it · ~90 min of live coding · comp-lib

This is the session that used to be the week-3 cliff. In F25 it carried Tailwind, classnames, tailwind-merge, PropTypes, react-icons, the components-vs-pages conversation and React Router's internals — all in one class, three weeks after they learned what a prop is.

This version does one component. Every library arrives because a concrete problem demands it, in the order the problems actually appear. The Accordion is class B; Router is week 5.

The through-line worth saying out loud: a <Button> is not a prettier <button>. It is a decision your whole team stops re-making.

Highlighted lines are what you add or change in that step. Everything else is already on screen. In print they are marked + in the left gutter.

Step 1Start from the starter

Copy starter/comp-lib out of the class repo into your own folder, then install and run. Don't work inside the class repo — you'll get merge conflicts next time you pull.

Tailwind is already wired up in vite.config.js and src/index.css. Two things to notice, because every tutorial you find online will be out of date:

  • Tailwind v4 is a Vite plugin. There is no tailwind.config.js and no postcss.config.js.
  • One @import 'tailwindcss' replaces the old @tailwind base/components/utilities trio, and theme values live in CSS in an @theme block.
At the podium
  • Show index.css and vite.config.js on the projector for 60 seconds, then move on. They don't need to configure Tailwind, they need to know why the internet's instructions won't match.
  • Get the dev server running for everyone BEFORE you start teaching. Anyone whose Tailwind classes do nothing has skipped npm install.
  • Sanity check together: add className="text-red-500" to something, save, see it go red. If that doesn't work, nothing today will.

Step 2Why not just use <button>?

Before we write anything: put three buttons on the page with different colours, using plain Tailwind classes on plain <button> elements.

It works. So why are we here? Because on a real team, that bg-blue-500 gets typed by fourteen people in forty places, half of them pick bg-blue-600 by accident, and when the brand colour changes somebody spends a day with find-and-replace.

A component library is one answer to that: make the decision once, in one file.

At the podium
  • Write this version live, let it work, then delete it. Five minutes. The point is that they feel the duplication before you solve it.
  • Ask the room: 'what happens when marketing changes the blue?' Let someone say find-and-replace, then ask what they'd miss.
  • This is also your chance to say what a design system is, in one sentence, without a lecture.

import Button from '../components/Button' const ButtonPage = () => {  return (    <>      <h1 className="text-3xl mb-4">Button Page!</h1>       {/* the version we are NOT going to keep */}      <button className="px-8 py-3 border bg-blue-500 border-blue-500 text-white">        Buy Now      </button>      <button className="px-8 py-3 border bg-green-500 border-green-500 text-white">        Success      </button>      <button className="px-8 py-3 border bg-red-600 border-red-600 text-white">        Delete      </button>    </>  )} export default ButtonPage

Step 3Variants as boolean props

How should somebody ask for a blue button? Not by passing color="blue" — blue is a colour, not a meaning. They ask for primary, danger, success. The component decides what those look like.

In JSX a bare attribute is shorthand for ={true}, so <Button primary> passes primary: true.

First pass: do it the obvious ugly way, with string building. It works, and it's about to get unmanageable.

At the podium
  • <Button primary> vs <Button primary={true}> — show both, they're identical. This shorthand confuses people for weeks if you skip it.
  • Name the design idea: props describe INTENT (danger), not appearance (red). Ask what happens if the danger colour becomes orange.
  • Let the string concatenation look bad. Don't apologise for it — the next step is the payoff.
src/components/Button.jsx
const Button = (props) => {  const {children, primary, success, danger} = props   // The obvious way. Watch how badly this scales.  let classes = 'px-8 py-3 border '  if (primary) classes += 'bg-blue-500 border-blue-500 text-white'  if (success) classes += 'bg-green-500 border-green-500 text-white'  if (danger) classes += 'bg-red-600 border-red-600 text-white'   return <button className={classes}>{children}</button>} export default Button

Step 4classnames: conditional classes without the mess

classnames (imported as cx by convention) takes an object of 'class name': condition pairs and returns a string of the classes whose condition was truthy.

cx('px-8', {'bg-blue-500': primary, 'bg-red-600': danger})

It also ignores undefined and null, which turns out to matter a lot later. Remember that.

At the podium
  • console.log(classes) and show the string it produces for two different prop combinations. Thirty seconds, and cx stops being magic.
  • Flag the ignores-undefined behaviour now and tell them you'll come back to it in step 9. You will.
  • Add secondary and warning here so all five variants exist — it's mechanical, let them type it while you walk.
terminal
$ npm install classnames
src/components/Button.jsx
import cx from 'classnames' const Button = (props) => {  const {children, primary, secondary, success, warning, danger} = props   // For each key/value pair: apply the key if the value is truthy.  const classes = cx('px-8 py-3 border', {    'bg-blue-500 border-blue-500 text-white': primary,    'bg-gray-900 border-gray-900 text-white': secondary,    'bg-green-500 border-green-500 text-white': success,    'bg-orange-400 border-orange-500 text-white': warning,    'bg-red-600 border-red-600 text-white': danger,  })   return <button className={classes}>{children}</button>} export default Button

Step 5Modifiers: rounded and outline

Colour variants are mutually exclusive — you pick one. Modifiers are different: rounded and outline combine with any colour.

outline needs the text to take the variant's colour instead of white, so the conditions get compound: outline && primary.

Save this and look closely at the outline buttons. Something is wrong.

At the podium
  • Do NOT fix the bug in this step. Let them see white-on-white and ask about it. That question is what earns the next library.
  • Ask why text-white is winning even though text-blue-500 comes later in the object. Someone will say 'later wins' — this is the moment to correct that: CSS doesn't care what order you list classes in the attribute, only what's in the stylesheet.
src/components/Button.jsx
import cx from 'classnames' const Button = (props) => {  const {    children,    primary,    secondary,    success,    warning,    danger,    rounded,    outline,  } = props   const classes = cx('px-8 py-3 border', {    // colour variants -- pick one    'bg-blue-500 border-blue-500 text-white': primary,    'bg-gray-900 border-gray-900 text-white': secondary,    'bg-green-500 border-green-500 text-white': success,    'bg-orange-400 border-orange-500 text-white': warning,    'bg-red-600 border-red-600 text-white': danger,    // modifiers -- combine with any colour    'rounded-full': rounded,    'bg-white': outline,    'text-blue-500': outline && primary,    'text-gray-900': outline && secondary,    'text-green-500': outline && success,    'text-orange-400': outline && warning,    'text-red-600': outline && danger,  })   return <button className={classes}>{children}</button>} export default Button

Step 6tailwind-merge: settling the fight

Our outline buttons get both text-white (from the colour variant) and text-green-500 (from outline && success). Both are real classes in the stylesheet. Which wins is decided by Tailwind's stylesheet order, not ours — and we lose.

tailwind-merge understands Tailwind's class groups. Given two classes that set the same property, it keeps the last one and drops the other. Wrap the whole cx(...) in twMerge(...).

At the podium
  • console.log the classes before and after twMerge, side by side. You can literally see text-white get removed. Best thirty seconds of the session.
  • This is a genuinely hard concept — specificity vs source order — and it's fine if only half of them fully get it. What they need to retain: twMerge resolves conflicts, last one wins.
  • In F25 this was the bug I hit live. It is not a mistake in your notes; it's inherent to the pattern.
terminal
$ npm install tailwind-merge
src/components/Button.jsx
import cx from 'classnames'// twMerge resolves conflicting tailwind classes -- the last one wins.// Without it, an outline button keeps the `text-white` from its// colour variant and you get white text on a white background.import {twMerge} from 'tailwind-merge' const Button = (props) => {  const {    children,    primary,    secondary,    success,    warning,    danger,    rounded,    outline,  } = props   const baseClass = 'flex items-center px-8 py-3 border'   const classes = twMerge(    cx(baseClass, {      // colour variants -- pick one      'bg-blue-500 border-blue-500 text-white': primary,      'bg-gray-900 border-gray-900 text-white': secondary,      'bg-green-500 border-green-500 text-white': success,      'bg-orange-400 border-orange-500 text-white': warning,      'bg-red-600 border-red-600 text-white': danger,      // additional style props      'rounded-full': rounded,      'bg-white': outline,      'text-blue-500': outline && primary,      'text-gray-900': outline && secondary,      'text-green-500': outline && success,      'text-orange-400': outline && warning,      'text-red-600': outline && danger,    })  )   return <button className={classes}>{children}</button>} export default Button

Step 7What if somebody passes two variants?

<Button primary danger> is nonsense, but nothing stops it. A component library should say so.

Count the variant booleans and warn in the console when more than one is true.

A note on prop-types: the library everyone's tutorials use for this is effectively dead. React 19 no longer calls propTypes on function components — the checks are silently ignored, which is worse than having none. Do it by hand like this, or use TypeScript, which is where the industry went and which we cover later in the semester.

At the podium
  • Say the prop-types thing plainly. Every tutorial they find will use it, and they need to know it's a no-op now — otherwise they'll 'add validation' that does nothing.
  • Number(!!primary) — unpack it: !! coerces to boolean, Number turns it into 0 or 1. Two small JS ideas in four characters.
  • Trigger the warning live with <Button primary danger> and show the console. Then remove it.

Step 8onClick is broken (and so is everything else)

Add an onClick to one of the buttons on the page. Click it. Nothing happens.

Of course not — we destructured the props we care about and threw the rest away. onClick never reaches the real <button>.

The rest parameter ...otherProps collects everything we didn't name, and spreading it onto the button forwards the lot: onClick, onMouseOver, type, disabled, aria-label — things we haven't thought of yet.

At the podium
  • Break it first. Add the onClick, click, get nothing, then ask why. Somebody will work it out and it'll stick.
  • console.log(otherProps) to show what's in there.
  • Bigger idea worth naming: a good wrapper component doesn't take away what the underlying element could do. Ask what would happen to a screen reader user if aria-label got dropped.

Step 9…but now className collides

Try <Button primary className="mb-5">. The margin doesn't apply — and worse, look at the order of our JSX: {...otherProps} spreads a className, then our own className={classes} overwrites it entirely.

Remember cx ignoring undefined? Here's the payoff. Put otherProps.className first inside cx, so a caller's classes are part of the merge — present when they pass one, harmlessly ignored when they don't. And because twMerge keeps the last of any conflicting pair, their mb-5 wins over ours.

At the podium
  • Show the broken version in the elements inspector — the className attribute really does only have our classes. Concrete beats explanation.
  • This is the single most sophisticated idea in the session. If you're running long, this is the step to do slowly and cut step 10 instead.
  • Callback to step 4: 'I told you the undefined thing would matter.'

Step 10Icons, and one global rule

react-icons bundles most of the big icon sets — Font Awesome, Material, Github's Octicons — and gives them all the same API. We'll use it again for the Accordion next class.

Icons go in as children, at the usage site, not as a prop: the Button doesn't need to know which icon you want.

The icon ends up jammed against the text. You could pass a margin class at every usage — but that's a decision you'd re-make forty times, which is the thing we're here to avoid. One global rule in index.css instead.

At the podium
  • The flex items-center in our base class is why the icon lines up vertically. Worth pointing at — it was doing nothing visible until now.
  • Ask where the margin rule should live: on every usage, in the component, or global? Let them argue for a minute. The global rule is a defensible call, not the only one.
  • If you're short on time, cut this step. It's the least load-bearing.
